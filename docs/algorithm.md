# beatmania IIDX 33 Sparkle Shower — NOTES RADAR 算法分析

目标二进制：`E:\IIDX\33_Sparkle_Shower\contents\bm2dx.dll`
（18,467,992 字节，2026-10-15 构建，ImageBase `0x180000000`）

> 本文里的所有地址都是 **RVA = 实际地址 − 模块基址**，写成 `0x180xxxxxx` 时是按首选基址
> 0x180000000 展开的绝对地址，换机器/换构建需要重新定位。

---

## 0. 结论速览

1. 谱面雷达（NOTES RADAR）是 6 个 **定点整数**，单位是 **1/100**，即 `20000 = 200.00`。
2. 每张谱面的 6 个值由 **6 个原始指标** 经过一个 **4 段折线归一化函数** 得到，函数输出范围
   `[0, 2.0]`，再乘 `10000` 取整。
3. **200.00 的"上限"不是一条 `min(v,200)` 指令** —— 它是折线函数最后一段的终点：
   `1.75 + 0.25 × 1.0 = 2.0`。所以全库搜 `200.0f` 搜不到雷达代码，原因就在这里。
4. 玩家雷达（PNR / `spradar`/`dpradar`）= 各谱面「谱面雷达 × 成绩率」按项目取前 10 曲求和 ÷ 10，
   因为谱面雷达最大 200.00，PNR 的最大值天然也是 200.00。
5. 因此"让谱面上限超过 200"＝把最后一段的截断去掉；"PNR 仍按 200 结算"＝在结算/上报处夹住 20000。

---

## 1. 雷达的存储形式

### 1.1 谱面雷达

每个谱面（music × chart index，chart index 0..9 = SP B/N/H/A/L + DP N/H/A/L/…）在内存里存 6 个 int32：

```
music_object + 0x4FC + (chart_index * 0x18) + (axis * 4)       // 6 * int32
```

依据：`0x180952e63` 处的"全曲雷达批量计算"循环

```
0x180952ed6  call 0x180826af0        ; 解析谱面 -> 10 * 0x230 的中间记录
0x180952f43  lea  rdx, [rsp+0x30]
0x180952f48  mov  rcx, rsi           ; 第 i 张谱面的记录
0x180952f4b  call 0x180827610        ; 记录 -> 6 个 int32（本函数的输出指针）
0x180952f50  mov  ecx, [rbx+rax]
0x180952f53  mov  [rdi+rbx], ecx     ; rdi = music + 0x4FC + i*0x18
0x180952f5a  cmp  rbx, 0x18
0x180952f60  inc  ebp                ; i++
0x180952f7c  cmp  ebp, 0xa           ; 10 张谱面
```

同一段里还能看到 `music+0x47C + i*4` 写的是该谱面的 **物量（notes 数）**，`music+0x400 + i*8`
写的是另外两个整型字段。

### 1.2 玩家雷达（PNR）

eamuse player data 的构造处 `0x180ad1291` 附近：

```
0x180ad1270  i = 0 / 1                       ; 0=SP, 1=DP
0x180ad1281  if (playerdata[0x36D8 + i*0x34]) {
0x180ad1291      node = new("notes_radar");  attr style = i
0x180ad12eb      ptr  = playerdata + 0x36A8 + i*0x34
0x180ad12fe      addBinary(node, "radar_score", ptr, 6)
             }
```

所以：

| 字段 | 偏移 |
|---|---|
| SP 雷达 6×int32 | `playerdata + 0x36A8` |
| DP 雷达 6×int32 | `playerdata + 0x36DC`（0x36A8 + 0x34） |
| SP/DP 有效标志 | `playerdata + 0x36D8 + i*0x34` |

服务器侧的存档（本机 asphyxia）里就是这 6 个数，例如：

```json
"spradar":[12764,12697,7600,7445,6334,14764]   // = 127.64 / 126.97 / 76.00 / 74.45 / 63.34 / 147.64
```

### 1.3 轴顺序

轴顺序固定为（见 `0x180cb3e90` 起的字符串 `radartype_notes` … `radartype_chord`）：

```
0 NOTES   1 PEAK   2 SCRATCH   3 SOFLAN   4 CHARGE   5 CHORD
```

调试导出函数 `0x180846bb0`（写 `/dev/raw/radar_<时间戳>.txt`）把 6 个值按
`Notes, Scratch, Peak, Chord, Charge, Soflan` 的列顺序打印，即内部下标 `0,2,1,5,4,3`。

## 2. 核心：`0x180827610` —— 指标 → 雷达值

### 2.1 参数表

`0x180CEF8B0` 起是一张 **12 × 16 字节（4 个 float）** 的参数表，前 4 个 float 是公共系数，
后面 12 个结构体 = 2 个 playstyle × 6 个轴：

```
0x180CEF8B0  1.2   1.25  1.75  2.2      ; 公共：段末值 1.0/1.5/1.75/2.0 的"基准"
0x180CEF8C0  300   0     0     0

0x180CEF8D0  160    500    15.3   108    \
0x180CEF8E0  145    500    15.4   113    |
0x180CEF8F0  440    1200   20.5   136    |  这 12 个结构体按"栈上排列顺序"
0x180CEF900  400    1200   20.0   170    |  重排后才是 (SP: A/B/C/D) 与 (DP: A/B/C/D)
0x180CEF910  10.2   70     1.4    440    |
0x180CEF920  10.4   70     1.4    440    |
0x180CEF930  2.6    1000   280    1000   |
0x180CEF940  2.6    1000   310    1010   |
0x180CEF950  6.2    3800   900    1450   |
0x180CEF960  7.0    4000   750    1500   |
0x180CEF970  17.9   122    3.9    2000   |
0x180CEF980  17.7   125    3.9    2000   /
```

函数在 `0x18082764B`–`0x1808276C4` 里把这 12 个向量搬到一个 24-float 的栈数组，
顺序是：

```
SP: [10.2, 70, 1.4, 440]  [160, 500, 15.3, 108]  [2.6, 1000, 310, 1010]
    [17.7, 125, 3.9, 2000] [440, 1200, 20.5, 136] [6.2, 3800, 900, 1450]
DP: [10.4, 70, 1.4, 440]  [145, 500, 15.4, 113]  [2.6, 1000, 280, 1000]
    [17.9, 122, 3.9, 2000] [400, 1200, 20.0, 170] [7.0, 4000, 750, 1500]
```

把它按「4 个断点 × 6 个轴」重排，就得到 **每个轴的 4 个断点 p0..p3**：

| 轴 | SP 断点 p0/p1/p2/p3 | DP 断点 p0/p1/p2/p3 |
|---|---|---|
| 0 NOTES   | 10.2 / 15.3 / 17.7 / 20.5 | 10.4 / 15.4 / 17.9 / 20.0 |
| 1 PEAK    | 70 / 108 / 125 / 136      | 70 / 113 / 122 / 170      |
| 2 SCRATCH | 1.4 / 2.6 / 3.9 / 6.2     | 1.4 / 2.6 / 3.9 / 7.0     |
| 3 SOFLAN  | 440 / 1000 / 2000 / 3800  | 440 / 1000 / 2000 / 4000  |
| 4 CHARGE  | 160 / 310 / 440 / 900     | 145 / 280 / 400 / 750     |
| 5 CHORD   | 500 / 1010 / 1200 / 1450  | 500 / 1000 / 1200 / 1500  |

> 交叉验证：日本社区在 IIDX 30 用穷举法测出的 PEAK 断点是 SP「70 → 100.00、108 → 150.00、
> 136 → 200.00」、DP「70 → 100、113 → 150、125 → 175、170 → 200」，与上表逐项吻合。
> 这也反证了上表的重排是正确的。

### 2.2 归一化函数

对每个轴 `d`（输入 `x = metric[d]`）：

```
if (x <= p0)      r = clamp(x / p0, 0, 1)                 // 0.00 .. 100.00
else if (x <= p1) r = 1.0  + 0.5  * (x-p0)/(p1-p0)        // 100.00 .. 150.00
else if (x <= p2) r = 1.5  + 0.25 * (x-p1)/(p2-p1)        // 150.00 .. 175.00
else              r = 1.75 + 0.25 * clamp((x-p2)/(p3-p2),0,1)  // 175.00 .. 200.00

out[d] = (int)(r * 10000)                                  // 1/100 定点
```

对应汇编（`0x1808277A0` 起到 `0x180827B35` 是 6 个轴展开 + 两趟循环）：

```
; 常量
0x1808276F8  movss xmm4, 1.0        ; 0x180E8229C
0x180827700  movss xmm5, 0.25       ; 0x180E82260
0x180827710  movss xmm6, 0.5        ; 0x180E82278
0x180827720  movss xmm7, 1.5        ; 0x180C9DB08
0x180827731  movss xmm8, 1.75       ; 0x180CEF8B8
0x180827745  movss xmm9, 10000.0    ; 0x180E82368   <- 最后乘 10000

; 最后一段（例：轴 0）
0x180827884  movss   xmm3, [rbp+rdx-0x68]   ; p3
0x180827891  comiss  xmm0, xmm3             ; x vs p3
0x180827894  jae     0x1808278AE            ; x >= p3 -> r = 1.0   ★这就是"200 上限"
0x1808278A0  subss   xmm0, xmm2             ; (x - p2)
0x1808278A4  subss   xmm3, xmm2             ; (p3 - p2)
0x1808278A8  divss   xmm0, xmm3
0x1808278AE  movaps  xmm0, xmm4             ; ← 被 jae 跳到的"1.0"分支
0x1808278B1  mulss   xmm0, xmm5             ; * 0.25
0x1808278B5  addss   xmm0, xmm8             ; + 1.75   => 最大 2.0
0x1808278BA  ...
0x1808278C0  movss   [rsp+rdx+0x38], xmm0   ; 保存 r
0x1808278C6  mulss   xmm0, xmm9             ; * 10000
0x1808278CB  cvttss2si eax, xmm0
0x1808278D8  mov     [rsp+rdx+0x20], eax    ; out[d]
```

**关键**：`jae 0x1808278AE` 这条分支就是 200.00 上限的全部来源。把它 NOP 掉，
`x > p3` 时就会落到 `(x-p2)/(p3-p2)` 分支，比值 > 1，`r > 2.0`，于是 `out > 20000`，
而且**保持单调**（不是简单地把 200 改成某个固定更大的数）。

同一条 `jae` 在函数里出现 3 次（展开后的 3 份拷贝，两趟循环覆盖 6 个轴）：

| 站点 | 指令 |
|---|---|
| `0x180827894` | `73 18` = `jae +0x18` |
| `0x1808279C1` | `73 18` |
| `0x180827AEE` | `73 18` |

### 2.3 6 个"指标"是什么

`0x180827560` 负责把谱面中间记录换算成 6 个 float 指标（输出到 `rdx` 指向的 6 个 float），
调用自 `0x180827610`：

```
0x180827579  mov edx, [rcx+0x98]
0x18082757F  mov ecx, [rcx+0x0C]
0x180827582  call 0x180827B90        ; 返回值 = (float)ecx * 1000.0 / (float)edx
...
0x180827587  cvttss2si ecx, [r8+0x210]
0x18082758B  call 0x180827B90        ; 第二项
0x180827598  movzx eax, byte [r8+0x154]
0x1808275A0  movzx edx, byte [r8+0x155]
0x1808275A8  movss xmm2, [r8+0x214]
0x1808275B3  movss xmm3, [r8+0x218]
0x1808275BF  movss xmm4, [r8+0x20C]
```

`0x180827B90` 就是 `(float)a * 1000.0f / (float)b`（b<=0 时返回 0）。结合调试导出里的
表头 `NPS / SPS / PEAK / CHORD / CN / SOFLAN`，可以确认这 6 个指标是**按每秒计的密度**一类的量：

| 轴 | 指标 | 断点数量级 |
|---|---|---|
| NOTES | 总物量 / 演奏时长（NPS） | 10–20 /s |
| PEAK | 某个时间窗内的最大物量 | 70–170 个 |
| SCRATCH | 皿 / 秒 | 1.4–7 /s |
| SOFLAN | BPM 变化相关量 | 440–4000 |
| CHARGE | CN / 秒 | 145–900 |
| CHORD | 同时押 / 秒 | 500–1500 |

> 社区结论：NOTES 对"总物量÷演奏时间"线性；PEAK 是「约 4 秒窗口内的最大物量」再做分段映射，
> SP 的整数上限 136、DP 170，断点在 100/150/175 处改变斜率 —— 与 `2.2` 的折线完全一致。

### 2.4 与实测数据对账

把 `2dxtra.sqlite` 的 `charts` 表（每张谱面的 `radar_*`，单位同样是 1/100）当作真值，用 NOTES 轴验证：

| 谱面 | notes | radar_notes | 反推 NPS = radar/100/100*10.2 | 反推时长 |
|---|---|---|---|---|
| 1000 / N | 92 | 1116 (11.16) | 1.138 | 80.8 s |
| 1000 / H | 779 | 8460 (84.60) | 8.63 | 90.3 s |
| 30000 / A | 2158 | 18387 (183.87) | 18.69（第 4 段） | 115.5 s |

同一首歌不同难度反推出的时长不同（80.8 / 90.3 s）符合"初级谱面提前结束"的直觉；
`183.87` 落在第 4 段（175–200）也说明分段点正确。另外该表 48372 张谱里有大量值**恰好等于 20000**，
证明"200.00 是硬截断而不是自然极限"。

## 3. 玩家雷达（PNR）的结算

社区实测 + 服务器存档结构，规则是：

```
对每个轴 a：
    contribution(chart, a) = chart_radar[chart][a] * (score / max_score)   // 成绩率
    PNR[a] = Σ(每个曲目取该曲所有难度里最大的 contribution)[前 10 曲] / 10
```

- 每个曲目只取"该曲所有难度中的最大值"参与，10 **曲**不是 10 谱面；
- 上限天然是 `200.00 × 1.0 = 200.00`；
- 27–29 曾有 FAILED 减半、AUTO SCRATCH 皿归零、LEGACY CN 归零等修正，30 以后取消。

所以：一旦谱面雷达可以 >200，`contribution` 也会 >200，PNR 就会突破 200.00 ——
这正是需求里"结算仍按 200.00"要挡住的地方。

**拦截点**：`0x180AD72B0` 是 eamuse 的 `addBinary` 包装，PNR 序列化时
`r8 = "radar_score"`、`r9 = playerdata + 0x36A8 + i*0x34`、元素个数 6。
在它里面就地把 6 个 int32 夹到 `[0, 20000]`，既改了上报值，也改了内存里的 PNR
（后续雷达界面读同一块内存，因此显示也回到 ≤200.00）。

## 5. 修改方案（已实现为 `notesradar.dll`）

1. **放开谱面上限**：把 `0x180827894 / 0x1808279C1 / 0x180827AEE` 三处的 `73 18`（`jae`）改成
   `90 90`（NOP）。`x > p3` 时不再走"比值=1.0"分支，而是继续线性外推，
   谱面雷达可以自然超过 200.00，并且仍然单调、保留排序。
   - 选曲画面、副屏读的都是 `music+0x4FC` 这份数据，所以两处同时生效。
2. **PNR 仍按 200 结算**：hook `0x180AD72B0`，当 `r8 == "radar_score"` 时把 `r9` 指向的
   6 个 int32 夹到 `20000`。
3. 两处都可单独开关（`notesradar.ini`）。

### 风险 / 注意

- 所有地址都是**按 18,467,992 字节这一版**定的；DLL 里做了字节签名校验，
  不匹配就跳过并写日志，不会乱改。
- 谱面雷达 >200 时，六边形会画到框外（游戏按 /200 归一化画图），属于预期现象。
- PNR 在"上报/存档"时夹到 200.00，并在随后 3 秒内每 16 ms 再夹一次，
  所以结算后雷达界面也会停在 200.00。更细的"逐项 contribution 就用 200"没有做，
  因为没有定位到唯一的 PNR 更新函数（见 §6.3）。

## 6. 2dxtra 兼容与结算封顶（第二轮）

### 6.1 为什么 2dxtra 谱面不生效

`2dxtra.dll`（4,950,016 字节）里 RVA `0x8820` 是一个"把缓存值写回谱面对象"的函数：

```
void write(rcx=music, dl=difficulty, r8=data) {
    switch (difficulty) {
    case 3:  notes@0x47C, radar@0x4FC; break;   // slot 0
    case 1:  notes@0x480, radar@0x514; break;   // slot 1
    case 0:  notes@0x484, radar@0x52C; break;   // slot 2
    case 2:  notes@0x488, radar@0x544; break;   // slot 3
    case 4:  notes@0x48C, radar@0x55C; break;   // slot 4
    case 7:  notes@0x494, radar@0x58C; break;   // slot 6
    case 6:  notes@0x498, radar@0x5A4; break;   // slot 7
    case 8:  notes@0x49C, radar@0x5BC; break;   // slot 8
    case 10: notes@0x4A0, radar@0x5D4; break;   // slot 9
    }
    // [music+notes_off] = data->notes;
    // movups [music+radar_off]      = data[0..3]
    // movsd  [music+radar_off+0x10] = data[4..5]
}
```

radar 偏移统一是 `music + 0x4FC + slot*0x18`，正好就是 §1.1 里游戏自己写的那个数组。
也就是说 **2dxtra 把 sqlite 里存的历史雷达值（早就被 200.00 夹过）直接盖回内存**，
把游戏本次算出的 >200 值冲掉了；而且它的值域封顶 20000，光靠改计算函数救不回来。
`charts` 表里 `radar_*` 的最大值就是 20000，也印证了这一点。

### 6.2 兼容做法：写入后取 max

hook `0x8820`：先保存目标槽位的 6 个 int，调用原函数，再逐项取 `max(旧值, 新值)`。

- 游戏本次算出 250、2dxtra 写 200 → 保留 250；
- 游戏没算过（槽位是 0）、2dxtra 写 200 → 保留 200（退化成原行为，不会更糟）。

钩子实现：入口 9 字节是 `48 85 C9 / 0F 84 78 01 00 00`（`test rcx,rcx` / `je`），
换成 `E9 rel32 + 90×4` 跳到 `.text` 里一段 14 字节以上的 `int3` 洞，
洞里放绝对跳转 `FF 25 00000000 <hook>`；trampoline 重放 `test/je` 后跳回 `entry+9`。

**仍未覆盖的情况**：如果游戏从来没给 2dxtra 谱面算过雷达（槽位一直是 0），
那取 max 也只能保留 sqlite 的 200.00。日志里会出现
`2dx: slot empty before write ...`，看到这条就说明需要走"重算"路线
（调用 `0x180826AF0` 自己算一遍），风险较大，暂未启用。

### 6.3 结算封顶

PNR 只在两处可观测：`playerdata+0x36A8/0x36DC` 的 6 个 int，以及上报时的
`"radar_score"`。游戏内部真正写这 6 个值的地方没有唯一的固定偏移写点
（全库扫描 `disp==0x36A8` 只有读档初始化 `0x1805B9EDD` 和上报读取 `0x180AD12EB`），
所以没法在"逐项 contribution"层面夹 200。

采用的替代方案：

1. `addBinary("radar_score")` 时把 6 个值就地夹到 `[0,20000]`；
2. 记录该数组指针，在随后 3 秒内由守护线程每 16 ms 再夹一次。

效果：结算后不管游戏内部算出多少，PNR 数组和界面都会回到 ≤200.00，
上报给（在线/离线）服务器的值同样是 ≤200.00。在线/离线无法可靠区分，
因此这项一律生效。
